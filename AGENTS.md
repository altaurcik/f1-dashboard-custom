# Инструкции для работы над F1 Dashboard Custom

Эти правила действуют во всём репозитории. Явные указания пользователя имеют приоритет.
Общение и документация — на русском; имена в коде и существующие надписи интерфейса — в принятом стиле проекта.

## Начало работы и карта проекта

1. Прочитай `PROJECT_MAP.md`, `README.md` и инструкции `AGENTS.md` в затрагиваемых каталогах, если они появились.
2. Проверь `git status --short`. Сохраняй чужие и незакоммиченные изменения; не сбрасывай их ради своей задачи.
3. Найди путь данных и нужные точки входа по карте, затем проверь их по коду. Карта помогает навигации, но код — источник истины.
4. Если карты нет, составь её по фактической структуре до существенных изменений. Не выдумывай отсутствующие сервисы или возможности.

Поддерживай `PROJECT_MAP.md` в той же задаче, в которой меняешь архитектуру, маршруты, важные файлы,
поток данных, внешние интеграции, конфигурацию или команды запуска. Удаляй устаревшие сведения.
При обнаружении существенного расхождения исправь соответствующий раздел карты.
Для косметической правки без изменения устройства проекта обновление карты не требуется.

Карта должна содержать:

- назначение проекта и основной экран;
- стек, маршруты и ключевые каталоги с ответственностью модулей;
- поток реальных данных от источника до компонентов;
- команды запуска и проверки, переменные окружения без значений секретов;
- внешние зависимости и ограничения, отличающие реализованное от планируемого.

Используй относительные ссылки на существующие файлы. Не перечисляй каждый значок, зависимости в `node_modules`,
сгенерированные файлы или временные процессы. Не записывай PID, текущую гонку и другие быстро устаревающие сведения.
Не превращай карту в дневник задач: описывай текущее состояние системы.

## Продукт и достоверность данных

- Рабочий режим использует настоящие данные Formula 1. Не запускай `mock-realtime.py` и не подменяй данные
  демонстрационными без явного запроса пользователя. Тестовые фикстуры допустимы в изолированных проверках.
- Не выдавай успешный HTTP-ответ за наличие живого потока: проверяй подписку, сессию и поступление обновлений.
  Если сессия завершена, источник недоступен или данные устарели, сообщай это прямо.
- Не придумывай скорости, позиции, времена кругов и радиосообщения для заполнения пустого экрана.
  Расчётную позицию по мини-секторам отличай от точной телеметрии.
- Основной Live Timing выравнивается по референсу Formula 1 Dashboard. Боковую навигационную панель
  не добавлять: пользователь прямо исключил её. Сохраняй набор полей и способ их отображения в секциях;
  не заменяй карточки произвольными аналогами. Проверяй DOM, CSS и сетевые данные, а не только скриншоты.
- При правках адаптивности проверяй читаемость и доступность всех строк пилотов, масштабирование таблицы,
  переполнение и работу панелей при разных размерах экрана.

## Независимость и происхождение данных

- Требование пользователя: искать только бесплатные источники. Не делать платную подписку обязательной.
- Карта полей и проверенных источников — [DATA_SOURCES.md](DATA_SOURCES.md). Не подключать новые зависимости
  к backend/CDN Formula 1 Dashboard; существующие зависимости считаются техническим долгом до миграции.
- Для данных/геометрии/ассетов сохранять первичный источник, версию конфигурации трассы и условия использования.
  Скачанная локальная копия референса сама по себе не доказывает независимость.
- Проверять покрытие live отдельно от архивов. Бесплатный доступ к истории не означает бесплатную live-телеметрию.
  При отсутствии поля показывать отсутствие; не использовать скрытый fallback на сервер референса.

## UI UX Pro Max

- Для разработки, исправления и проверки интерфейсов используй установленный проектный скилл
  [UI UX Pro Max](.agents/skills/ui-ux-pro-max/SKILL.md). Перед работой прочитай его инструкции;
  команды запуска и происхождение — [.agents/skills/README.md](.agents/skills/README.md).
- Поиск запускай полным путём к локальному scripts/search.py; для этого проекта выбирай Next.js/React
  по задаче. Не использовать CLAUDE_PLUGIN_ROOT из upstream-примеров как путь этого проекта.
- Указания пользователя, визуальный референс, состав полей и отсутствие боковой панели имеют приоритет
  над общими рекомендациями скилла. Установка скилла сама по себе не означает смену дизайн-системы.

## Принципы разработки

- Делай минимальное законченное изменение, решающее задачу. Не добавляй несвязанный рефакторинг,
  новые библиотеки или универсальные абстракции без конкретной необходимости.
- Сохраняй границы: транспорт — `tools/f1-live.cjs` и `useSocket`; буферы и задержка — `useDataEngine`;
  состояние — Zustand; отображение — компоненты. Не размножай соединения с F1 внутри компонентов.
- TypeScript используй со строгими типами. Контракты данных держи в `src/types`;
  проверяй входные данные на границах системы и учитывай частичные обновления и отсутствующие поля.
- Не ломай имена SSE-событий `initial`/`update` и формат `CarDataZ`/`PositionZ` при изменении адаптера.
  При изменении контракта согласованно обновляй источник, типы и потребителя.
- Используй существующие UI-компоненты, Tailwind и настройки форматирования. Форматируй затронутые файлы;
  не запускай массовое форматирование репозитория ради локальной правки.
- Избегай лишних перерисовок при частых обновлениях: выбирай нужные поля Zustand, освобождай подписки,
  таймеры и соединения при завершении. Не нарушай задержку и паузу воспроизведения.
- Учитывай Windows и другие платформы. Не добавляй абсолютные пути конкретного компьютера в рабочий код;
  пути к внешним исполняемым файлам задавай через конфигурацию.
- Секреты оставляй в локальном окружении. Не выводи токены в логи, документацию, клиентский код или коммиты.
  В `.env.example` описывай только настройки и безопасные примеры.
- Не считай код в `.cache/f1-dash-services` частью поддерживаемого приложения:
  это локальная копия upstream. Постоянные изменения вноси в файлы этого репозитория.

## Запуск и проверки

Команды и порты описаны в `PROJECT_MAP.md`. Используй Yarn из `packageManager` и существующий `yarn.lock`;
не создавай параллельный lock-файл npm/pnpm. Перед запуском проверяй занятость портов и уже работающие процессы.
Не останавливай чужие процессы ради освобождения порта.

Проверки выбирай по изменению:

- документация: существование ссылок, точность команд и соответствие коду;
- TypeScript/React: проверка типов и применимые lint-проверки, затем проверка затронутого поведения;
- UI: просмотр затронутого экрана в браузере и проверка соответствующих размеров экрана;
- поток F1: синтаксис адаптера, `/api/health`, `/api/current`, SSE `initial`/`update`, CORS;
  для изменений переподключения также проверь восстановление соединения;
- сборка или конфигурация Next.js: production build с нужным окружением, когда изменение его затрагивает.

Добавляй содержательные тесты для сложной логики и регрессий, а не тесты, повторяющие реализацию.
Документация и простая визуальная правка сами по себе не требуют нового тестового набора.
Если проверка недоступна или падает из-за существующей проблемы, укажи конкретную причину;
не отключай проверки и не расширяй задачу незаметно.

В результате кратко сообщи, что изменено, какие проверки выполнены и какие ограничения остались.
Отметь обновление карты, если оно было нужно. Не коммить и не публикуй изменения без соответствующего запроса.
